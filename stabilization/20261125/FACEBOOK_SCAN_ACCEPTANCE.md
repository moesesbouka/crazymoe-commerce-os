# Facebook scanner acceptance

The production inventory page can remain a viewer during this rollout. Use a separate Studio database for signed-in acceptance so the production catalog and run tables remain read-only. Seed a seller-edited price, an active row absent from the test feed, and a second-account posting copy linked by its exact destination listing ID.

1. Apply the migration to the test database after the current Studio schema. In the test database, register the verified Facebook profile through `studio_register_facebook_scan_account` with the Studio owner. The existing catalog tag can be registered. The extension resolves the tag for the current Facebook viewer through the database binding.
2. Stage `install_facebook_scan_66013.py` against the verified work-PC `66.0.12` installation using the default staging mode. Use an isolated copy of the full extension, configured to point the scan worker and Studio extension login at the acceptance project with that project's publishable key. Sign in on Facebook Selling and to the matching acceptance Studio owner, then load the isolated build in Chrome. Keep the production scanner off during the test.
3. Start one observed scan of the registered account. Verify the bound tag, working elapsed time, discovery and save counts, and that closing and reopening the Studio panel leaves the run running. Record the feed completion reason, verify seller price and absent-row status and timestamps, and verify the old version and wrong profile are rejected.
4. In a separate controlled run, click Stop as the scanner saves. Verify already committed batches remain, no later batch writes, and fresh heartbeats cannot revive a stopped or disconnected run. Verify a repeated scan does not re-count known pending observations. Check the second account using the exact destination linkage fixture before registering it in production.
5. Once acceptance passes, recheck the live Vercel SHA and the active release row. Run `reconcile_manual_mercari_release.sql` only if they still match its guards. For the next deploy, stage the exact committed Studio web root and run `python stabilization/20261125/stamp_studio_release.py <deploy-root> --commit <release-sha>`. Verify the served `/version.json` and the Vercel deployment ID, then activate the corresponding Studio manifest. A missing or different SHA causes System Health to show ATTENTION.

The scanner update is version `66.0.13`. The original `66.0.12` lacks the profile and coverage contract and its start/write RPCs are disabled by the hardening migration. Account verification uses the current viewer identity visible to the authorized Chrome extension, together with the Studio owner binding. An actual Facebook response is required to verify the strict viewer and selling-feed parser against today's page. The local fixtures cover the contract and cannot supply that evidence.
